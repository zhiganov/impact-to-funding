# v0.7.0: claim objections, a check-back, mentors and sizing ideas

**Experimental source prerelease.** The release tag identifies its source commit.
This release covers changes since v0.6.0 (`22baece`).

## What changed in the skill

- **Look for what counts against a claim.** Before a claim goes into a public brief,
  report or profile, the agent offers one more step, which the person can skip. It
  finds the strongest objection, first in the supplied material and outside it only
  with permission, keeping private details out of searches. It says who gains if the
  claim is true, then keeps, narrows or marks the claim disputed rather than dropping
  it. The objection stays in the private assessment unless the person approves public
  wording. The support-brief playbook points to the step (#140, #141; issue #139).
- **An optional three-month check-back.** After finishing a task, the agent may offer,
  once, to ask four short questions in about three months: did you use it again, what
  for, did you show anyone, and what stopped you. Only the date is saved, in one small
  file in the person's home folder. If they answer, the agent can turn the answers into
  a pre-filled public note that the person reviews and submits on GitHub themselves.
  Nothing is sent by the agent. It needs a host that gives the skill's folder and
  allows local commands (#135; issue #134).
- **Mentors beyond people you already know.** The agent now helps find people,
  communities and mentoring programmes that could help, including people the builder
  doesn't know yet: maintainers of related projects, people whose public work fits the
  question, and programmes that pair mentors with newcomers. It uses only what those
  people made public, checks a programme's own page for whether it's open, and helps
  draft a short first message the person sends. There's still no mentor pool and no
  introductions (#145).
- **A quick sizing before committing time.** Before someone puts real time into an
  idea, the agent offers a short check they can skip: is it significant, wanted and
  feasible, what does it cost, and what early signal would show it's working. Rough
  estimates are said to be rough, and unknowns become the first things to check (#148).
- **Work whose effect is indirect.** New guidance for infrastructure, maintenance,
  tools for others and coordination: name who depends on the work, label hypothetical
  failures, ask the people who rely on it, say plainly what can't be measured, and ask
  for upkeep in its own right (#149).
- **Only one skill per package.** A maintainer guide was shipped as a second
  `SKILL.md`, and OpenCode listed it as a skill, `itf-release-notes`, when ItF was
  installed in `.agents/skills`. It's now a plain guide outside skill form, and a
  package test checks there's exactly one `SKILL.md` (#146).

## New or changed local tools

- **Check-back helper** (`tools/skill-package/check-back-entry.mjs`): reads and
  writes the check-back's one state file, and builds the pre-filled note link. It
  never contacts a network service. Commands: `opt-in`, `decline`, `link`, `done`,
  `forget` (#135).

## Use and updates

Existing copies don't update themselves.

- **Claude Code plugin:** `claude plugin update itf`, once this release's plugin is
  listed.
- **Codex, OpenCode and other agents:** `npx skills add zhiganov/impact-to-funding#v0.7.0`,
  or clone the `v0.7.0` tag. See the [installation guide](../install.md).
- **Managed CLI:** use the prerelease channel, or select the release's full commit.
