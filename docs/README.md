# Design context

The [audience and positioning note](audience-and-positioning.md) identifies agent-native
builders as the agreed initial primary audience while preserving broader users,
roles and lifecycle needs. Job loss and difficulty getting hired are one
important job to be done, not a universal audience condition. The intended
value also includes meaningful contribution, verifiable impact, peer/community
connections and potential financial support; these are not claims of existing
matching or funding services. Demand and usefulness remain unvalidated.

The [responsible-assistance guidance](responsible-assistance.md) explains the
source skill's conduct-based boundaries without a sector blacklist, mandatory
screening or moral ranking. Its [nine fictional cases](../examples/responsible-assistance.md)
are authored expectations, not observed model behaviour, legal clearance or
evidence of reliable enforcement. It changes no manifest format or licence.

[A case-grounded pattern language with framework lenses](pattern-language-design.md)
proposes linked cases, contextual patterns, optional lenses and private local
applications across open-ended domains. It is a design, not a curated collection,
validated pattern language, database or implemented skill feature. Broad case
collection and systems/complexity instruction changes remain separate scopes.

The separate [seed collection](../references/library/README.md) applies the design
through original source-linked notes and explicitly provisional pattern links.
It supplies neither comprehensive domain coverage nor validation of transfer to
a new setting. The [core skill](../SKILL.md#use-reference-knowledge-selectively)
conditionally reads relevant notes; this adds no database, live retrieval service
or systems/complexity method change.

The [reference-library MCP decision](reference-library-mcp-decision.md) selects an
independently usable interface with source in this public repository,
separate from funding/opportunity discovery. Canonical Markdown and bundled skill
use remain independent. This records an architecture boundary, not a tool contract,
implemented server, hosting commitment or requirement to use MCP.

The [accepted library MCP design contract](reference-library-mcp-contract.md) and
[entirely fictional walkthrough](../examples/reference-library-mcp-walkthrough.md)
define the initial `itf.library/0.1-draft` read-only discovery, detail and coverage
baseline for #44. The design preserves shared-file lens context and exact
snapshot/version limits; executable schemas, server implementation and verified
client compatibility are not established by these documents.

The [optional local library MCP](../mcp/README.md) implements that baseline with
stdio tools and separately prepared immutable public snapshots. Its
[implementation checks](reference-library-mcp-checks.md) record observed behaviour
and client-specific limits. It supplies no hosting, authentication, live ingestion
or change to ordinary bundled skill use.

[Optional Standard.site publishing and discovery](standard-site-publishing.md)
maps approved public reports to existing publication metadata and tools. It is
design only, not an exporter or publication trial; funding.json stays unchanged
and the skill remains usable through ordinary Markdown/manual reading.

[Reusable evidence and funder-specific reporting](evidence-reporting-design.md)
designs private evidence/claim links, proportionate collection planning, versioned
requirements interpretation and audience-specific crosswalks. Its
[fictional walkthrough](../examples/evidence-reporting.md) is not a model trial or
an implemented collector, provider adapter or new installed-skill capability.
Manual use does not depend on funding discovery or a hosted evidence store.

The source skill now conditionally routes to that manual guidance and the
[optional private evidence/crosswalk worksheet](../assets/evidence-crosswalk.md),
with links from the existing assessment and report templates. Its
[check record](evidence-reporting-checks.md) distinguishes source/template review
from model behaviour, native installation and actual funder interoperability.

[Broader support discovery and funding.json compatibility](funding-interchange-design.md)
reassesses the earlier webpage-only bridge. The
[accepted architecture](funding-interchange-direction-decision.md) selects a
domain-neutral ItF support profile, with optional upstream financial projection
and a same-file extension for appropriate OSS cases. Its
[field contract is now accepted](support-profile-baseline-decision.md) as a design
target; the [fictional examples](../examples/funding-interchange.md) are not
schema/consumer compatibility results. The later local implementation is linked
below; ItF is not restricted to OSS or FLOSS/fund's audience.

The [support-profile contract](support-profile-contract.md) specifies the accepted
fields, types, carrier, references, monetary semantics and loss-aware financial
projection, with reconciled fictional edge cases. Its separate field-contract
adoption establishes no schema implementation, exporter or consumer test.

The separate [local support-profile tools](support-profile-tools.md) implement
optional authoring, strict inspection, explicit financial-plan binding and
loss-aware financial views. They make no source/network/publication calls and do
not establish a working integration with a funding directory or other consumer.
Its [implementation check record](support-profile-checks.md) separates observed
local behaviour from untested consumer and installation claims.

[AI Registry and Vercel Skills CLI distribution references](ai-registry-distribution.md)
compare registry/catalog value with direct Git skill distribution, separately
from skills.sh discovery and impact evidence. Neither distribution tool has been
integrated or tested for ItF; native-host checks are documented separately.

[Voluntary user-feedback guide](user-feedback.md) and
[initial-user learning plan](user-learning-plan.md) describe historical manual-use
feedback preparation and an artifact/access assessment. They are not the current
native onboarding guide, and there is no active feedback collection through them.

The [native installation guide](install.md) covers project/personal folders,
host-specific invocation, safe updates/removal and troubleshooting. The
[check record](installation-check-2026-11-04.md) separates Codex's limited CLI
verification of `4566892`, a matching limited Claude Code check of the same
source, and earlier OpenCode checks of `fbb8993`. Personal installs,
interactive/IDE/desktop surfaces and human usefulness are not established by
the CLI checks.

[Release and update guidance](releases.md) explains optional GitHub release
notifications, deliberate version selection, source-versus-host-check boundaries
and the maintainer's release convention. The
[v0.2.0 release notes](releases/v0.2.0.md) describe the experimental source
prerelease; exact-package host verification remains separately bounded.

The [version/provenance contract](skill-version-provenance.md) and optional
[local inspector](../tools/skill-package/README.md) define released source,
explicit channels/pins and private installation observations. Those interfaces
remain read-only. The separate [managed CLI](managed-skill-updates.md) adds
explicit installation, check/update, adoption, rollback and recovery; neither
automatic notices nor new host-verification claims are included.

[Individual theories, shared projects and contribution portfolios](individual-project-contributions.md)
records the agreed conceptual relationship and core manual-use source implementation,
tracked in [#22](https://github.com/zhiganov/impact-to-funding/issues/22)
and the extended [#16](https://github.com/zhiganov/impact-to-funding/issues/16).
The [contribution reference](../references/contributions.md) supplies the operational
guidance. Source instructions and package checks do not establish native activation,
model adherence or a hosted tracker;
#16's collaborative workflow design remains separate work.

The [draft ItFtI/guilds concept note](guilds-itfti-atproto.md) and
[fictional Atmospheric Group walkthrough](../examples/guilds-itfti-atproto.md)
explore ItF users working together as guilds: shared practice, recognition and
learning before optional funding. They distinguish protocol permissions from
community governance and describe anti-capture questions, not a working integration.

The [native guild-workflow assessment](guild-workflow-assessment.md) completes
#53's offline cooperation journey and native mapping, reusing existing contribution,
decision and report designs. Its recommendation is documentation-only; implemented
collaboration, user usefulness and deployed Groups compatibility remain unverified.

The [guild-curation assessment](guild-curation-assessment.md) and
[fictional policy-change case](../examples/guild-curation.md) cover #52's offline
reuse/gap assessment: attributed policy-bound selections and optional personal/
collective views, without a new schema, registry, automatic ranking or certification.
Human-readable portability does not establish typed or native interoperability.

[The preserved scope snapshot](design-scope-2026-11-04.md) records the proposed product/method boundary at the time it was drafted. Its statements that implementation was unselected and licensing/publication undecided are historical. Current package status is in the [project README](../README.md); the [licence scope](../LICENSE) separates CC BY-SA 4.0 written content, MIT software and third-party exceptions while preserving earlier MIT grants.

The snapshot is retained verbatim. It is not a live task queue, a licence grant, a private evidence export, or approval for publication, integrations or money movement.
